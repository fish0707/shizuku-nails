# Shizuku.nails 雫｜平台升級計畫

> **目標**：在**不串金流**的前提下，把現有官網升級為「線上預約 ＋ LINE／IG 自動化 ＋ 會員經營 ＋ 客戶 360」的自有平台，能力對齊夯客這類預約 SaaS，同時保住自有網站在 SEO／GEO 上的優勢。
>
> 本文件寫給**人**看（你與老闆 Lilca）：說明現況、比較、決策、時程、費用與風險。
> 交給執行 Agent 的技術指令在 [`AGENT_PROMPT.md`](./AGENT_PROMPT.md)。

## 1. 現況盤點

### 1.1 目前架構

```
客人 ─► index.html / notice.html / booking.html     （Vercel 靜態網頁）
             │  ?action=getSlots（讀時段）
             │  POST action=booking（no-cors 送出）
             ▼
        GAS-A：預約 ＋ LINE 回覆 ◄── /api/webhook（Vercel Edge 轉送）◄── LINE 平台
             │
             ▼
        Google Sheets：時段列表、預約紀錄

index.html「加入會員名單」表單 ─► GAS-B ─► Google Sheets：會員名單
IG 作品集 ─► Behold widget（自動同步 IG 貼文）
```

兩個 Google Apps Script 專案（GAS-A、GAS-B）的原始碼**不在 repo 裡**，沒有版本控制。

### 1.2 已經做得好的

- 完整的 SEO／GEO：meta、OG、geo tags、BeautySalon／FAQPage／Breadcrumb JSON-LD、`llms.txt`、AI 爬蟲全開放的 `robots.txt`、sitemap 已通過 Google Search Console
- 四步驟線上預約流程（選服務 → 選時段 → 填資料 → 確認），手機體驗不錯
- 品牌視覺完整、IG 作品自動同步

### 1.3 發現的問題

| 嚴重度 | 問題 | 影響 |
|---|---|---|
| 🔴 | **價格散在 5 處且不一致**：卡片與 `booking.html` 用低價組（$600 起），下拉選單、JSON-LD、FAQ Schema、`llms.txt` 用高價組（$1,600 起）；加購的延甲也不同（$100／指最多 3 指 vs $150／指最多 2 指） | 客人爭議；Google 規定 Schema 價格須等於頁面可見價格；AI 可能對外報錯價 |
| 🔴 | **遲到規則三種說法**：首頁 5 分鐘、須知頁 10 分鐘、預約頁 15 分鐘 | 執行規則時有爭議空間 |
| 🔴 | 預約用 `no-cors` 送出，前端**讀不到伺服器回應** | 送出失敗或時段已被訂走，客人仍看到「預約成功」；若 GAS 寫入前沒檢查，就會重複預約 |
| 🔴 | 預約碼在**前端用亂數產生、沒有送到後端** | 客人傳「預約確認 BFxxxx」時，後端無從比對是哪一筆 |
| 🔴 | LINE webhook **沒有驗證簽章**（X-Line-Signature） | 任何人都能偽造 LINE 事件打進系統 |
| 🟠 | Edge function 轉送 GAS 時沒有 `waitUntil` | 回應送出後背景請求可能被中斷，LINE 事件遺失 |
| 🟠 | 預約用**試算表列號**（slotRowIndex）指向時段 | 老闆插入／刪除／排序列，預約就會對到錯的時段 |
| 🟠 | 時段不考慮服務時長（法式約 2 小時） | 時段可能互相重疊 |
| 🟠 | 客人**手打 LINE ID**，系統拿不到 LINE userId | **無法自動推播提醒**，這是做提醒功能最大的阻礙 |
| 🟠 | GAS 原始碼不在 repo | 無版本紀錄、無法 code review、壞了難以還原 |
| 🟡 | 殘留其他專案痕跡（"beauty fish"、`BF` 前綴、給 webhook 用的 sessionStorage——webhook 根本讀不到瀏覽器資料） | 維護困惑 |
| 🟡 | webhook 把完整訊息內容寫進 log | 個資外洩風險 |
| 🟡 | Tailwind 使用 Play CDN（官方定位為開發用） | 效能較差、不建議正式環境使用 |
| 🟡 | 收集姓名、電話但沒有完整的隱私權政策頁 | 個資法風險；LINE Login 與 Meta 審核也會要求 |

## 2. 與夯客類預約 SaaS 比較

|---|---|---|---|

| 品牌設計 | ✅ 客製 | 模板 | ✅ 客製 |
| 線上預約 | 🟡 有，但有漏洞 | ✅ | ✅ 資料庫層級防重複 |
| 時段管理 | 🟡 老闆在試算表逐列開 | ✅ | ✅ 每週模板 ＋ 例外日 |
| 預約成立通知 | 🟡 客人要自己傳「預約確認」 | ✅ 自動 | ✅ 自動 |
| 預約前提醒 | ❌ | ✅ | ✅ |
| 客人自助改期／取消 | ❌ | ✅ | ✅（自動套用規則） |
| LINE 自動回覆／圖文選單 | 🟡 有限 | ✅ | ✅ |
| IG 私訊整合 | ❌ | 視方案 | ✅（需通過 Meta 審核） |
| 會員資料 | 🟡 一張試算表 | ✅ | ✅ |
| 客戶 360 | ❌ | 🟡 通用型 | ✅ **美甲專屬**：甲型、長度、色系、過敏、歷次作品照 |
| 爽約／遲到管理 | ❌ 靠人工記 | ✅ | ✅ 自動計次 ＋ 停權規則 |
| 回訪提醒 | ❌ | 視方案 | ✅ 依每位客人自己的回訪週期 |
| 老闆後台 | ❌ | ✅ | ✅ 手機優先 |
| 營運報表 | ❌ | ✅ | ✅ |
| 金流／POS | ❌ | ✅ | ❌ **刻意不做**（僅手動記錄實收金額） |
| 資料所有權 | ✅ 自有 | 平台 | ✅ 自有 |
| 月費 | $0 | 月費 | 低（見第 6 節） |

**結論**：完成後的平台在預約與會員經營上對齊夯客類 SaaS，並在三件事上做得更好——**被搜尋與被 AI 推薦的能力、美甲專屬的客戶 360、資料完全自有**。唯一刻意缺席的是金流。

## 3. 目標架構與關鍵決策

### 3.1 目標架構

```
              ┌──────────────── Vercel（Next.js）────────────────┐
Google／AI ──►│ 行銷頁（靜態輸出）：/、/notice、服務頁…             │
              │   內容來自資料庫，老闆在後台按「發布」即重建        │
LINE 客人 ───►│ LIFF：/book 預約、/my 我的預約（自動取得 LINE 身分） │
老闆 ────────►│ /admin 後台（手機優先，可加到主畫面）               │
LINE 平台 ───►│ /api/line/webhook ─┐                               │
Meta 平台 ───►│ /api/ig/webhook  ──┼─► 業務邏輯 ─► Supabase         │
排程器 ──────►│ /api/cron/dispatch ┘   │          （資料庫・檔案・登入）│
              │                        └─► LINE／IG 發訊 API        │
              └──────────────────────────────────────────────────┘
```

### 3.2 關鍵決策

| 決策 | 原因 |
|---|---|
| **Google Sheets → Supabase（Postgres）** | 防止重複預約需要資料庫層級的約束；客戶 360 需要關聯式資料；GAS 讀不到 HTTP header，無法驗證 LINE 簽章（這也是當初要多一層 Vercel 轉送的原因） |
| **靜態 HTML → Next.js** | 行銷頁依然輸出靜態 HTML，SEO／GEO 不受影響；同時才有辦法做後台與 LIFF。所有網址維持不變或 301 轉址 |
| **LIFF 取代手打 LINE ID** | 拿到 LINE userId 才能推播提醒，這是整套自動化的前提 |
| **提醒走 LINE，IG 只當詢問入口** | IG 規定只能在客人最後一則訊息後 24 小時內回覆，**不能主動推播提醒** |
| **所有自動訊息走「排程佇列」** | 預約成立時就把提醒排進佇列，取消預約即撤銷，避免重複發或漏發 |
| **不使用 LINE Notify** | 該服務已於 2025/3/31 終止 |
| **預約先「待確認」，老闆核准後才送地址** | 符合目前「預約完成才提供地址」的隱私做法；可在設定中改為自動確認 |
| **保留老闆「開放固定時段」的習慣** | 一人工作室通常公布幾個開始時間（例如 10:00、14:00、18:00），系統以每週模板產生，並自動依服務時長檢查衝突 |

## 4. 分階段計畫

| 階段 | 內容 | 預估工作量 | 老闆要參與的事 |
|---|---|---|---|
| **0** | 地基、止血、決策 | 約 1 週 | 確認價目與規則、開帳號 |
| **1** | 新架構 ＋ SEO 無損遷移 ＋ 內容後台 | 1–2 週 | 試用後台改價格 |
| **2** | 預約引擎 ＋ LIFF ＋ 預約管理後台 | 約 2 週 | 試約、驗收 |
| **3** | LINE 自動化與提醒 | 1–2 週 | 確認訊息文案 |
| **4** | IG 私訊整合 | 約 1 週 ＋ Meta 審核等待 | 配合 Meta 審核 |
| **5** | 會員經營 ＋ 客戶 360 | 約 2 週 | 確認會員分級規則 |
| **6** | 報表 ＋ SEO 擴充 | 約 1 週 | — |

> 工作量為粗估，實際依 Agent 執行效率與外部審核時間而定。每階段結束都會在測試網址驗收，**確認沒問題才上線**。

### Phase 0｜地基、止血、決策
- **業主確認**（阻擋後續所有工作）：正確價目與加購、統一遲到／改期／累犯規則、開放時段模式、預約要自動確認還是人工核准
- 價格與規則確認後，**先在現有網站把所有地方統一**（卡片、下拉、預約頁、JSON-LD、FAQ、`llms.txt`）
- 修補現有 webhook：簽章驗證、`waitUntil`、移除個資 log
- 取得兩個 GAS 專案原始碼與試算表，存檔進 repo
- 帳號前置：網域決策、Vercel 方案、Supabase、LINE Developers、IG 專業帳號
- **IG 可行性查核**：Meta App Review／商家驗證是否需要營業登記——若需要而目前沒有，Phase 4 改走備案

### Phase 1｜新架構 ＋ SEO 無損遷移 ＋ 內容後台
- 建立 Next.js ＋ Supabase，**原樣移植**現有視覺
- 服務、價格、加購、FAQ、預約須知、網站標題等全部進資料庫
- 頁面卡片、預約選單、JSON-LD、`llms.txt`、sitemap、LINE 自動回覆**全部從同一份資料產生**——價格不一致從此不可能發生
- 老闆後台：登入、改內容、按「發布」
- 驗收：所有 SEO 項目逐一比對無遺失、Google Rich Results Test 通過、網址不變

### Phase 2｜預約引擎 ＋ LIFF
- 每週時段模板 ＋ 例外日（休假、加開）
- 依服務時長自動檢查衝突，**資料庫層級保證不會重複預約**
- 從 LINE 開啟預約頁自動帶入身分；可上傳目前甲況照片（取代「請到 LINE 傳照片」）
- 「我的預約」：查看、改期、取消（自動套用提前天數規則）
- 老闆後台：行事曆、核准／拒絕、標記完成／爽約／遲到、填寫實收金額
- 可訂閱到手機行事曆（iCal）
- 從試算表搬移既有預約

### Phase 3｜LINE 自動化與提醒
- 加好友歡迎訊息、圖文選單（線上預約／我的預約／價目／作品集／須知／聯絡老闆）
- 關鍵字自動回覆（價格、地點、預約方式、補甲），答案來自同一份 FAQ 資料
- 預約成立卡片、**前一天提醒**（附「確認出席／我要改期」按鈕）、術後保養、**7 天免費補甲提醒**、依個人週期的**回訪提醒**、生日訊息
- 深夜不發送；監控每月推播額度
- 新預約通知老闆
- 切換 LINE webhook，退役舊 GAS

### Phase 4｜IG 私訊整合
- 接收 IG 私訊、24 小時內自動回覆常見問題並導向預約頁
- IG 對話併入客戶 360
- **備案**（若 Meta 審核不通過）：使用 Meta Business Suite 內建的 IG 自動回覆 ＋ 帶追蹤參數的預約連結

### Phase 5｜會員經營 ＋ 客戶 360
- 客戶資料：基本資料、LINE／IG 身分合併、標籤、備註
- **美甲專屬偏好**：甲型、長度、喜歡的色系與風格、過敏或敏感、甲況
- 每次來店紀錄 ＋ 前後對照照片（作品公開使用需另外同意）
- 自動計算：來店次數、累計金額、平均回訪週期、上次來店、爽約／遲到次數
- **累犯自動停權**（依須知規則，老闆可手動解除）
- 會員分級（依來店次數，不涉及金流）
- 分眾推播（依標籤、分級、久未回訪）
- 個資：同意紀錄、資料匯出、刪除申請

**客戶 360 頁面長這樣**：最上面是姓名、LINE／IG 頭像、分級、標籤與風險提示（例如爽約 1 次）；接著是數字（來店 8 次、累計 $9,600、平均 26 天回訪、上次 23 天前）；中間是時間軸（每次預約、每則 LINE／IG 訊息、老闆備註混在一起依時間排列）；下方是美甲偏好與歷次作品照；右上角快速動作：幫她預約、傳訊息、加備註。

### Phase 6｜報表 ＋ SEO 擴充
- 報表：每週預約數、時段使用率、爽約率、回訪率、熱門服務與加購、實收營業額、**客人從哪裡來**（Google／IG／LINE／AI 推薦／朋友介紹）
- SEO 擴充：各服務獨立頁（瞄準「台中法式美甲」等長尾關鍵字）、作品案例頁、評估建立 Google 商家檔案
- 術後訊息邀請客人留下評論，累積真實評價後才加入星等結構化資料

## 7. 風險與對策

| 風險 | 對策 |
|---|---|
| Meta 審核或商家驗證需要營業登記 | Phase 0 先查核；不通過就走 Meta Business Suite 內建自動回覆備案 |
| LINE 推播額度不夠 | 提醒項目可個別開關；監控用量；確認通知改用免費回覆 |
| 遷移期間影響現有預約 | 新舊並行、測試網址驗收、保留舊 GAS 兩週作為退路 |
| 測試時誤發訊息給真客人 | 開發一律使用另開的測試用 LINE 官方帳號 |
| SEO 排名在遷移後掉落 | 逐項比對 SEO 清單、網址不變或 301、上線後盯 Search Console 兩週 |
| 個資法 | 隱私權政策頁、明確同意、最小蒐集、資料刪除流程、後台登入保護 |
| 之後才換網域 | Phase 0 就決定 |
| GAS 原始碼拿不到 | 依現有前端行為與試算表結構重建邏輯 |

## 8. 成功指標

Phase 0 先量測目前數值當基準，上線後追蹤：

- **爽約率**（主要目標）
- 老闆每週花在 LINE 來回確認的時間
- 回訪率、平均回訪間隔
- 預約來源分布（特別是 AI 推薦帶來的比例）
- Google Search Console 自然搜尋點擊與曝光

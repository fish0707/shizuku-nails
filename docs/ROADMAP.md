# 預約制服務業｜平台升級計畫（通用模板）

> **目標**：在**不串金流**的前提下，把預約制服務業者（美甲、美睫、髮廊等）的現有官網，升級為「線上預約 ＋ LINE／IG 自動化 ＋ 會員經營 ＋ 客戶 360」的自有平台，能力對齊夯客這類預約 SaaS，同時保住自有網站在 SEO／GEO 上的優勢。
>
> 本文件寫給**人**看（專案負責人與業主）：說明盤點方式、比較、決策、時程、費用與風險。
> 交給執行 Agent 的技術指令在 [`AGENT_PROMPT.md`](./AGENT_PROMPT.md)，使用前先填寫其中第 0 節的專案參數。

## 1. 現況盤點（Phase 0 執行）

### 1.1 典型起點

多數中小型預約制業者的現況長這樣，盤點時依實際情況修改：

```
客人 ─► 官網（靜態頁或架站平台）
             │  讀時段／送出預約
             ▼
        Google Apps Script（或表單服務）◄── 轉送層 ◄── LINE 平台
             │
             ▼
        Google Sheets：時段、預約、會員名單

預約確認、改期、提醒 ─► 業主在 LINE 上人工來回處理
IG 作品 ─► 嵌入 widget 或手動更新
```

### 1.2 常見問題檢查清單

盤點時逐項確認，結果填入「是否存在」欄：

| 嚴重度 | 檢查項目 | 影響 | 是否存在 |
|---|---|---|---|
| 🔴 | **同一個價格散在多處且不一致**（服務卡片、預約頁、表單選單、JSON-LD、FAQ、`llms.txt`） | 客人爭議；Google 規定 Schema 價格須等於頁面可見價格；AI 可能對外報錯價 | |
| 🔴 | **同一條規則有多種說法**（遲到幾分鐘、改期提前幾天） | 執行規則時有爭議空間 | |
| 🔴 | 預約用 `no-cors` 等方式送出，前端**讀不到伺服器回應** | 送出失敗或時段已被訂走，客人仍看到「預約成功」 | |
| 🔴 | 預約碼在**前端產生、沒有存到後端** | 客人拿預約碼來查詢或確認時，後端無從比對 | |
| 🔴 | LINE webhook **沒有驗證簽章**（X-Line-Signature） | 任何人都能偽造 LINE 事件打進系統 | |
| 🟠 | Serverless／Edge 函式在回應後執行背景工作，卻沒有 `waitUntil` | 背景請求可能被中斷，LINE 事件遺失 | |
| 🟠 | 預約以**試算表列號**指向時段 | 業主插入／刪除／排序列，預約就會對到錯的時段 | |
| 🟠 | 時段不考慮服務時長 | 長時間的服務與下一個時段重疊 | |
| 🟠 | 客人**手打 LINE ID**，系統拿不到 LINE userId | **無法自動推播提醒**，這是做提醒功能最大的阻礙 | |
| 🟠 | 後端程式（例如 Apps Script）**不在版本控制中** | 無修改紀錄、無法 code review、壞了難以還原 | |
| 🟡 | 殘留其他專案的名稱、前綴或無效程式碼 | 維護困惑 | |
| 🟡 | 把訊息內容、電話、姓名寫進 log | 個資外洩風險 | |
| 🟡 | 使用 Tailwind Play CDN（官方定位為開發用） | 效能較差、不建議正式環境使用 | |
| 🟡 | 收集姓名、電話但沒有完整的隱私權政策頁 | 個資法風險；LINE Login 與 Meta 審核也會要求 | |

另外盤點並存檔：現有 SEO 項目清單（作為遷移後的比對基準）、設計 token、Search Console 驗證方式、近三個月預約與爽約數（作為成效基準）。

## 2. 與夯客類預約 SaaS 比較

> 下表「夯客類」欄位為一般預約 SaaS 的典型能力。夯客官方資料顯示其提供預約、會員、POS 並整合 LINE 官方帳號；細部功能與價格請以其最新官方資訊為準。

| 能力 | 典型起點 | 夯客類預約 SaaS | 本計畫完成後 |
|---|---|---|---|
| SEO／GEO（被搜尋、被 AI 推薦） | 🟡 視現有網站而定 | ⚠️ 通常弱（平台網域、JS 渲染） | ✅ 完整並擴充 |
| 品牌設計 | ✅ 客製 | 模板 | ✅ 客製 |
| 線上預約 | 🟡 表單或試算表，常有漏洞 | ✅ | ✅ 資料庫層級防重複 |
| 時段管理 | 🟡 業主手動開時段 | ✅ | ✅ 每週模板 ＋ 例外日，支援多位服務人員 |
| 預約成立通知 | ❌ 人工回覆 | ✅ 自動 | ✅ 自動 |
| 預約前提醒 | ❌ | ✅ | ✅ |
| 客人自助改期／取消 | ❌ | ✅ | ✅（自動套用規則） |
| LINE 自動回覆／圖文選單 | 🟡 有限 | ✅ | ✅ |
| IG 私訊整合 | ❌ | 視方案 | ✅（需通過 Meta 審核） |
| 會員資料 | 🟡 一張試算表 | ✅ | ✅ |
| 客戶 360 | ❌ | 🟡 通用型 | ✅ **產業專屬**偏好欄位與歷次作品照 |
| 爽約／遲到管理 | ❌ 靠人工記 | ✅ | ✅ 自動計次 ＋ 停權規則 |
| 回訪提醒 | ❌ | 視方案 | ✅ 依每位客人自己的回訪週期 |
| 業主後台 | ❌ | ✅ | ✅ 手機優先 |
| 營運報表 | ❌ | ✅ | ✅ |
| 金流／POS | ❌ | ✅ | ❌ **刻意不做**（僅手動記錄實收金額） |
| 資料所有權 | ✅ 自有 | 平台 | ✅ 自有 |
| 月費 | 低 | 月費 | 低（見第 6 節） |

**結論**：完成後的平台在預約與會員經營上對齊夯客類 SaaS，並在三件事上做得更好——**被搜尋與被 AI 推薦的能力、依產業客製的客戶 360、資料完全自有**。唯一刻意缺席的是金流。

## 3. 目標架構與關鍵決策

### 3.1 目標架構

```
              ┌──────────────── Vercel（Next.js）────────────────┐
Google／AI ──►│ 行銷頁（靜態輸出）：首頁、須知、服務頁…             │
              │   內容來自資料庫，業主在後台按「發布」即重建        │
LINE 客人 ───►│ LIFF：預約、我的預約（自動取得 LINE 身分）          │
業主 ────────►│ /admin 後台（手機優先，可加到主畫面）               │
LINE 平台 ───►│ /api/line/webhook ─┐                               │
Meta 平台 ───►│ /api/ig/webhook  ──┼─► 業務邏輯 ─► Supabase         │
排程器 ──────►│ /api/cron/dispatch ┘   │          （資料庫・檔案・登入）│
              │                        └─► LINE／IG 發訊 API        │
              └──────────────────────────────────────────────────┘
```

### 3.2 關鍵決策

| 決策 | 原因 |
|---|---|
| **試算表 → Supabase（Postgres）** | 防止重複預約需要資料庫層級的約束；客戶 360 需要關聯式資料；Google Apps Script 讀不到 HTTP header，無法驗證 LINE 簽章 |
| **現有網站 → Next.js** | 行銷頁依然輸出靜態 HTML，SEO／GEO 不受影響；同時才有辦法做後台與 LIFF。所有網址維持不變或 301 轉址 |
| **LIFF 取代手打 LINE ID** | 拿到 LINE userId 才能推播提醒，這是整套自動化的前提 |
| **提醒走 LINE，IG 只當詢問入口** | IG 規定只能在客人最後一則訊息後 24 小時內回覆，**不能主動推播提醒** |
| **所有自動訊息走「排程佇列」** | 預約成立時就把提醒排進佇列，取消預約即撤銷，避免重複發或漏發 |
| **不使用 LINE Notify** | 該服務已於 2025/3/31 終止 |
| **預約可設為「待確認」，核准後才送地址** | 適用不公開地址的工作室；公開地址的店家可設為自動確認 |
| **時段以「每位服務人員的每週開始時間」設定** | 符合小型工作室公布固定時段的習慣，系統依服務時長自動檢查衝突 |
| **客戶偏好欄位依產業設定** | 同一套系統可套用美甲、美睫、髮廊等不同產業 |

## 4. 分階段計畫

| 階段 | 內容 | 預估工作量 | 業主要參與的事 |
|---|---|---|---|
| **0** | 盤點、止血、決策 | 約 1 週 | 確認價目與規則、開帳號 |
| **1** | 新架構 ＋ SEO 無損遷移 ＋ 內容後台 | 1–2 週 | 試用後台改價格 |
| **2** | 預約引擎 ＋ LIFF ＋ 預約管理後台 | 約 2 週 | 試約、驗收 |
| **3** | LINE 自動化與提醒 | 1–2 週 | 確認訊息文案 |
| **4** | IG 私訊整合 | 約 1 週 ＋ Meta 審核等待 | 配合 Meta 審核 |
| **5** | 會員經營 ＋ 客戶 360 | 約 2 週 | 確認會員分級規則與產業欄位 |
| **6** | 報表 ＋ SEO 擴充 | 約 1 週 | — |

> 工作量為粗估，實際依現有網站複雜度、服務人員數、Agent 執行效率與外部審核時間而定。每階段結束都在測試網址驗收，**確認沒問題才上線**。

### Phase 0｜盤點、止血、決策
- 依第 1.2 節檢查清單盤點，列出所有價格與規則出現的位置
- **業主確認**（阻擋後續所有工作）：正確價目與加購、統一遲到／改期／累犯規則、開放時段、預約要自動確認還是人工核准
- 確認後**先在現有網站把所有地方統一**，作為止血
- 修補可立即修的安全問題：webhook 簽章驗證、`waitUntil`、移除個資 log
- 取得不在 repo 的後端原始碼與資料，存檔進 repo
- 帳號前置：網域決策、Vercel 方案、Supabase、LINE Developers、IG 專業帳號
- **IG 可行性查核**：Meta App Review／商家驗證是否需要營業登記；若需要而業者沒有，Phase 4 改走備案

### Phase 1｜新架構 ＋ SEO 無損遷移 ＋ 內容後台
- 建立 Next.js ＋ Supabase，**原樣移植**現有視覺
- 服務、價格、加購、FAQ、預約須知、網站標題等全部進資料庫
- 頁面卡片、預約選單、JSON-LD、`llms.txt`、sitemap、LINE 自動回覆**全部從同一份資料產生**——價格不一致從此不可能發生
- 業主後台：登入、改內容、按「發布」
- 驗收：對照 Phase 0 的 SEO 基準清單逐一比對無遺失、Google Rich Results Test 通過、網址不變

### Phase 2｜預約引擎 ＋ LIFF
- 每位服務人員的每週時段模板 ＋ 例外日（休假、加開）
- 依服務時長自動檢查衝突，**資料庫層級保證同一位服務人員不會被重複預約**
- 多位服務人員時客人可指定或不指定
- 從 LINE 開啟預約頁自動帶入身分；可上傳參考照片
- 「我的預約」：查看、改期、取消（自動套用提前天數規則）
- 業主後台：行事曆、核准／拒絕、標記完成／爽約／遲到、填寫實收金額
- 可訂閱到手機行事曆（iCal）
- 從舊系統搬移既有預約與會員

### Phase 3｜LINE 自動化與提醒
- 加好友歡迎訊息、圖文選單（線上預約／我的預約／價目／作品集／須知／聯絡我們）
- 關鍵字自動回覆（價格、地點、預約方式等），答案來自同一份 FAQ 資料
- 預約成立卡片、**前一天提醒**（附「確認出席／我要改期」按鈕）、服務後關懷、**保固／免費修補期限提醒**、依個人週期的**回訪提醒**、生日訊息
- 深夜不發送；監控每月推播額度
- 新預約通知業主
- 切換 LINE webhook，退役舊系統

### Phase 4｜IG 私訊整合
- 接收 IG 私訊、24 小時內自動回覆常見問題並導向預約頁
- IG 對話併入客戶 360
- **備案**（若 Meta 審核不通過）：使用 Meta Business Suite 內建的 IG 自動回覆 ＋ 帶追蹤參數的預約連結

### Phase 5｜會員經營 ＋ 客戶 360
- 客戶資料：基本資料、LINE／IG 身分合併、標籤、備註、慣用服務人員
- **產業專屬偏好欄位**（例：美甲記錄甲型與色系、美睫記錄捲度與膠水過敏、髮廊記錄染燙紀錄與髮質）
- 每次來店紀錄 ＋ 前後對照照片（作品公開使用需另外同意）
- 自動計算：來店次數、累計金額、平均回訪週期、上次來店、爽約／遲到次數
- **累犯自動停權**（依須知規則，業主可手動解除）
- 會員分級（依來店次數，不涉及金流）
- 分眾推播（依標籤、分級、久未回訪）
- 個資：同意紀錄、資料匯出、刪除申請

**客戶 360 頁面長這樣**：最上面是姓名、LINE／IG 頭像、分級、標籤與風險提示（例如爽約 1 次）；接著是數字（來店 8 次、累計 $9,600、平均 26 天回訪、上次 23 天前）；中間是時間軸（每次預約、每則 LINE／IG 訊息、業主備註混在一起依時間排列）；下方是產業偏好欄位與歷次作品照；右上角快速動作：幫他預約、傳訊息、加備註。

### Phase 6｜報表 ＋ SEO 擴充
- 報表：每週預約數、時段使用率、爽約率、回訪率、熱門服務與加購、實收營業額、**客人從哪裡來**（Google／IG／LINE／AI 推薦／朋友介紹）
- SEO 擴充：各服務獨立頁（瞄準「地區＋服務名稱」長尾關鍵字）、作品案例頁、評估建立 Google 商家檔案
- 服務後訊息邀請客人留下評論，累積真實評價後才加入星等結構化資料

## 5. 業主需要準備／決定的事

**第一優先（Phase 0 就要）**
- [ ] 確認正確價目表（含所有加購）

- [ ] 預約要「自動成立」還是「業主核准後才成立」

## 6. 費用估算

> ⚠️ 以下皆需在 Phase 0 查證現行方案。

| 項目 | 方案 | 費用 | 注意 |
|---|---|---|---|
| Vercel | Hobby／Pro | $0／約 US$20 每月 | Hobby 方案條款限**非商業**使用，營業用途應評估升級 Pro |
| Supabase | Free | $0 | 有容量上限；閒置一段時間會暫停（每日排程可避免）；免費版無時間點還原，需自建備份 |
| LINE 官方帳號 | 免費方案 | $0 | **主動推播每月有則數上限**，提醒會消耗額度；回覆訊息不計 |
| Meta／IG API | — | $0 | 需通過 App Review |
| 網域 | .tw／.com | 約 NT$400–1,000／年 | |
| Email 通知（選用） | 免費方案 | $0 | |

**LINE 推播額度估算方式**：每筆預約約消耗 3 則推播（前一天提醒、服務後關懷、回訪提醒）。預約成立通知可設計成由客人端觸發、用免費的「回覆」送出，不吃額度。以每月 60 筆預約為例約需 180 則，再對照 LINE 現行方案的額度判斷是否需要升級。多位服務人員的店家預約量較大，更需要事先試算。

## 7. 風險與對策

| 風險 | 對策 |
|---|---|
| Meta 審核或商家驗證需要營業登記 | Phase 0 先查核；不通過就走 Meta Business Suite 內建自動回覆備案 |
| LINE 推播額度不夠 | 提醒項目可個別開關；監控用量；確認通知改用免費回覆 |
| 遷移期間影響現有預約 | 新舊並行、測試網址驗收、保留舊系統兩週作為退路 |
| 測試時誤發訊息給真客人 | 開發一律使用另開的測試用 LINE 官方帳號 |
| SEO 排名在遷移後掉落 | 對照基準清單逐項比對、網址不變或 301、上線後盯 Search Console 兩週 |
| 個資法 | 隱私權政策頁、明確同意、最小蒐集、資料刪除流程、後台登入保護 |
| 之後才換網域 | Phase 0 就決定 |
| 舊後端原始碼拿不到 | 依現有前端行為與資料結構重建邏輯 |

## 8. 成功指標

Phase 0 先量測目前數值當基準，上線後追蹤：

- **爽約率**（主要目標）
- 業主每週花在 LINE 來回確認的時間
- 回訪率、平均回訪間隔
- 預約來源分布（特別是 AI 推薦帶來的比例）
- Google Search Console 自然搜尋點擊與曝光
